# A Raspberry Pi 5, Mesa V3D 7.1.7.0, release build, fan fitted, idle at 57 C,
# `vcgencmd get_throttled` clean before and after.
#
#   cargo xtask bench --skip llvmpipe --check tests/bench-baselines/raspberry-pi-5-v3d.txt
#
# `--skip llvmpipe` because measuring the software rasterizer locks this board
# up; see docs/on-a-board.md.
#
# Checked against three fresh runs on the board it came from: all eight rows
# within three tenths of a percent in every one of them, which is what says this
# board can gate at all.
#
# Updating this is a reviewed event, like the shader snapshots: re-record with
# --record, and the diff is the claim that every row moved for a reason. The
# GLES rows repeat to about a tenth of a percent and mean what they say.
#
# All four *Vulkan* rows land in one of two states from one process to the next,
# and that sentence used to name only the distance-field one. Measured
# 2026-09-01 over sixteen runs across three commits: the four move together,
# every run is wholly in one state or the other, and the gap is 4.3 per cent on
# the distance field, 0.8 and 1.1 on the tessellated pair and 1.6 on the frame.
# So the explanation the older note gave -- the cost of recording a hundred and
# sixty draws -- cannot be the whole of it, since the tessellated rows submit
# one draw and move too. What it is has not been established from here.
#
# Each of those four therefore carries a fourth field, its own tolerance, wide
# enough to cover the other state. They are recorded in the faster one, which
# is the state to compare a change against; the tolerance is what keeps a run
# that landed in the slower one from reading as a regression. Before this the
# three unnamed rows had the default one per cent and failed on any slow-mode
# run, which is noise this file was producing rather than catching.
#
# Last checked against the board: 724158a
#
# That line names the commit whose state a board run passed against, which is
# never the commit that writes the line -- a hash cannot be recorded inside the
# object it names. So it is updated afterwards, in a commit that touches nothing
# the bench times, and the count below it stays honest.
#
# It is read by `cargo xtask gate`, which counts the commits touching what the
# bench times since it and says so. It exists because the numbers below
# once went sixteen renderer commits unchecked and were ten and a half per cent
# out, and nothing in the tree could have said so -- "I ran it" is not a fact a
# later reader can find. Update it when a `--check` run passes, whether or not
# the numbers are re-recorded.
#
# Re-recorded a fourth time on 2026-09-01, for one commit: `1f64a28`, which
# folded a rounded rectangle's fill and its outline into one expression. It was
# written for the duplication rather than for the clock, and the shader it left
# is 431 bytes of GLSL and 68 SPIR-V words smaller. What that bought, and cost:
#
#   vulkan full frame      14.444 -> 13.955   -3.4%   the row an interface pays
#   vulkan tessellated x4   4.481 ->  4.522   +0.9%
#   vulkan tessellated x1   3.661 ->  3.691   +0.8%
#   gles   full frame      14.540 -> 14.835   +2.0%
#
# Neither distance-field row moves, which is the part worth pausing on: that is
# the path the folded function serves. Whatever the four rows above are
# responding to, it is not the arithmetic that changed -- it is the size and
# shape of the program around it, differently on each backend's compiler. The
# same conclusion `docs/on-a-board.md` reaches from the other direction.
#
# `e9833c8` is in the same span and measures at nothing. It deleted a function
# nothing ever called -- 207 bytes of GLSL, 78 SPIR-V words -- and four runs of
# it against four of `1f64a28` alone are indistinguishable on all eight rows.
# The commit declined to claim a gain; this is the measurement that says there
# was none.
#
# Attributed by benching three commits over sixteen runs, four a side in the
# faster Vulkan state: `ce3b31f` before both shader commits reproduces the
# previous numbers exactly, `1f64a28` alone reproduces the ones below, and the
# tip is indistinguishable from `1f64a28`.
#
# Re-recorded a third time on 2026-09-01, and this one is a correction rather
# than a change. The numbers below had been recorded at `01119dd` and the
# checked-at line then moved forward to `259db30`, on the reasoning that a hash
# cannot be recorded inside the object it names. That reasoning is right and the
# commit it landed on was not: `259db30` changes what the bench times, and its
# own message says so -- "the distance-field benchmark came back four per cent
# faster on the Pi 5". So the line named a commit whose state had never passed,
# and the gate counted from the wrong place.
#
# Established by benching three commits, three runs each, on one board in one
# sitting. `01119dd` reproduces every row of the old numbers to within four
# tenths of a percent and passes. `259db30` moves four of the eight rows and
# fails on one. `5dfc1ff`, the eight commits since, is level with `259db30`
# everywhere -- the largest difference between them is a fifth of a percent, and
# the GLES analytic-stroke row reads 8.926/8.914/8.930 against 8.903/8.909/8.917,
# clusters that overlap.
#
# So the whole of the movement below belongs to `259db30`, which drew a stroke
# as the difference of two offset shapes:
#
#   vulkan distance field   9.225 -> 8.857   -4.0%   what its message claimed
#   gles   distance field   8.714 -> 8.919   +2.4%   what nobody noticed
#   vulkan full frame      14.623 -> 14.442  -1.2%
#   gles   full frame      15.033 -> 14.530  -3.3%
#
# The tessellated rows do not move, which is the check on that attribution: the
# change is to the analytic stroke and those four rows never take it.
#
# One row got slower and it is recorded rather than argued away. The commit is a
# net win on this board -- both full-frame rows and the Vulkan stroke row are
# faster, and the frame is what an interface pays -- but the GLES stroke row
# costs 2.4 per cent for it, and the two backends running the same WGSL is
# exactly why that is worth writing down rather than averaging out. It went
# unseen because the Vulkan row it is paired with carries a five per cent
# tolerance for its own bimodality, and the run that would have failed on GLES
# was never made.
#
# Re-recorded twice before that on 2026-09-01, for three fixes of one kind: work
# every fragment did that its own draw had not asked for.
#
# `shade` dispatched on the material kind with a chain of `if`s, so a fragment
# paid two float comparisons for each kind ahead of its own and a solid color
# fell through all fourteen. `fs_main` called `blend_tint` unconditionally --
# twenty-nine modes and the non-separable tail behind them -- to arrive at the
# one multiply that `Modulate`, the mode a draw that asked for nothing gets,
# actually means. And `dithered` computed which kinds dither before the
# amplitude test that discards the answer for every draw that is not a
# gradient's.
#
# Against what this file held on 2026-08-26, three runs a side agreeing to a
# hundredth of a millisecond: the tessellated rows fell by about three quarters,
# 13.661 to 3.694 and 15.976 to 4.523; the distance-field rows by a third; the
# mixed frame by a third and a quarter.
#
# Every pixel of all four hundred and twenty-six catalog and corpus scenes is
# byte-identical across both changes, checked by hashing each scene before and
# after. That check is not optional here and no test in the tree replaces it:
# both backends run the same WGSL, and the software reference is lavapipe
# running it too, so a shared mistake would pass every comparison the suite
# makes.
#
